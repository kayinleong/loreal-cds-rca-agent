## Purpose & entry points

An LLM-agnostic tool layer: no LLM calls in any tool. The host LLM (GitHub Copilot or Claude Code) writes the SQL, reasons, and writes the RCA. It has two transports that route to the same `_dispatch()` (`mcp_server.py:437-746`):

| Entry point | How it is launched | Who uses it today |
|---|---|---|
| **CLI harness** `run_tool.py` | `python rca_copilot_agent/run_tool.py <tool> --json '<args>'`. It parses JSON, runs the startup checks, then calls `_dispatch` (`run_tool.py:51-114`). | **Primary path.** Both instruction files tell the host to use the CLI: `.github/agents/rca_copilot.agent.md:8,22-28` (via `run_in_terminal`) and `.claude/skills/rca-copilot/SKILL.md:5,12-13` (via `Bash`). Reason given: "L'Oréal's environment does not allow MCP servers" (`AGENTS.md:51`). The switch was made in quick-017 (commit `1f01bc3`). |
| **MCP stdio server** `mcp_server.py` | Registered as `snow-mcp` in `.vscode/mcp.json` (venv python, `-u mcp_server.py`, sets `SNOW_INSTANCE`, `REPORTS_DIR`, `ATTACHMENTS_DIR`, `BQ_*`). It runs the startup checks once, then `stdio_server` (`mcp_server.py:836-908`). If the `mcp` SDK is missing it falls back to JSON-RPC (`:788-831`), which lists only 10 of the 14 tools (`:804-812`). | Legacy/alternate path. No instruction file references it any more. |

Config: `config.load_config()` reads env vars first, then `.env` (searching CWD, then the package dir) (`config.py:42-80`). `X_USERTOKEN` also accepts the aliases `X-UserToken` and `X-usertoken` (`:73-77`). Default data dirs are `rca_copilot_agent/my_reports` and `rca_copilot_agent/attachments` (`:78-79`). `.vscode/mcp.json` overrides them to the repo root.

## Orchestration (who drives the loop; prompt-enforced vs code-enforced sequencing)

- **The host LLM drives the loop.** No agent loop exists in this package. The instruction files tell the host to do the following:
  - **Step 0:** classify intent: URL → fetch; `INC\d+` → single; "all" → batch; "post comment" → post.
  - **Step 1:** `fetch_incidents` (URL), otherwise `list_incidents`.
  - **Step 2:** `analyze_incident`. If any identifier is present, call `list_bq_tables` → `get_schema` → `query_bigquery` (never skip BQ when identifiers exist; no speculative queries). Then write the RCA → `save_rca_report` → `send_rca_email` once, with no verification ask.
  - **Step 3:** only with post intent: show the RCAs, ask for confirmation, then `post_comment`.
  - Sources: `rca_copilot.agent.md:49-58,72-141`; `SKILL.md:43-123`.
- **Code-enforced ordering (only these):**
  1. Auth checks run before any tool, as process-start side effects. They are non-blocking on failure.
  2. `analyze_incident` internally sequences fetch → summary → identifiers → attachments (`mcp_server.py:521-585`).
  3. Email attaches only reports registered by `save_rca_report`, and only in the same process.
- **Prompt-only:**
  - the step order;
  - running BQ when identifiers exist;
  - LIMIT in every query;
  - schema lookup before querying;
  - the save-before-output rule ("If you skip this call, you have failed", `agent.md:54`);
  - one email per session;
  - post-comment confirmation;
  - the RCA template and canonical group names.
- Tool descriptions repeat these hints, e.g. `mcp_server.py:198-199` ("ALWAYS follow up with query_bigquery") and `:370-371`, `:393-394`. `_dispatch` itself is stateless and accepts any tool in any order.
- The Copilot agent restricts itself to `run_in_terminal` + `read_file` (`agent.md:60-61,263-264`). However, its frontmatter `tools:` grants only `execute/*` (`agent.md:9-19`), so `read_file` may not actually be available. SKILL.md has no tool restriction.

## Gaps vs target flow

1. **Auth is a startup side effect, not an explicit step (1a/1b).** No `ensure_login` / `check_auth` tool exists, and nothing refreshes mid-session. In CLI mode auth is re-checked on every call and can pop Edge or `gcloud auth login` repeatedly. Failures are swallowed, so the host never learns that auth failed until a downstream tool errors. The GCP domain check does not cover post-login or ADC.
2. **BQ access lacks cost guards (3).** The live path uses the `bq` CLI with no dry-run and no `maximum_bytes_billed`. The guarded `SafeBigQueryExecutor.execute()` and the ADC it needs are dead code. The `BQ_*` env vars in `mcp.json` are ignored.
3. **Delivery is broken in the primary (CLI) mode (5).** Session report tracking is in-memory, so `send_rca_email` sends no attachments. Shell single-quote JSON breaks on apostrophes in RCA text.
4. **Reading tickets (2):** there is no assignment-group targeting except through the user-supplied list URL. Attachment content is downloaded but never analysed (no OCR). Bulk fetch clobbers the combined cache.
5. **RCA production (4) is entirely prompt-enforced.** There is no structured validation of the four sections, and the template is triplicated with drift.

## Open questions

1. Is MCP mode (`.vscode/mcp.json` `snow-mcp`) still supported, or is CLI-only the target? The answer decides whether to fix the email attachments by persisting the session list to disk or by globbing `rca_reports/`.
2. Should the target flow's "authenticate" step become an explicit callable tool (e.g. `check_auth`), run once per session rather than per CLI call?
3. Should `query_bigquery` move back to the python client (ADC + dry-run + `maximum_bytes_billed`), or add `--dry_run` and `--maximum_bytes_billed` flags to the `bq` CLI call? Which credential store does L'Oréal policy allow?
4. Which assignment groups should "read tickets" target by default? Today it is whatever the list URL encodes.
5. Is OCR/vision on attachments expected? The repo CLAUDE.md mentions "OCR'd images", but this package does none, and the Copilot agent forbids reading attachment files.
6. Edge is hard-coded (`auth_tool.py:83`). Is Edge guaranteed on all analyst machines (macOS)?
