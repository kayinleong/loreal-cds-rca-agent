1.  Purpose & objectives
This guidebook captures the knowledge transfer session run by Dipti for the L2 / L3 team. The session focused on building a shared mental model of how CDS, legacy systems, and downstream systems work together, and on standardising how the team analyses and responds to incidents.
The expectation is clear:
L2 / L3 must not jump to conclusions or fixes. Proper analysis must come first.

By following this guide, the team should be able to:
	•	Independently analyse incidents before escalating.
	•	Identify what to check, in what order, and why.
	•	Reduce incorrect RCAs, unnecessary checks, and mis-routed tickets.
	•	Apply consistent investigation logic across markets and brands.
	•	Respond to clients with evidence — screenshots, timestamps, and a clear logical conclusion.

Before touching any incident, hold this picture in mind. Almost every analysis turns on understanding which system created or now owns the data.

5.  Key identifiers you must understand
5.1  LUCID — L'Oréal Unique Consumer ID
	•	Generated only by CDS.
	•	Global, unique consumer identifier.
	•	Same email or mobile within a country → same LUCID across brands.
	•	Different email and different mobile → different LUCID.

LUCID prefix
Meaning
C2
Migrated consumer (sourced from LS)
C5
Ongoing consumer (created after go-live via real-time API)

5.2  Mars ID
	•	Generated by Mars after CDS sends consumer data.
	•	Multiple Mars IDs can exist for one consumer, but only ONE is active at any time.
	•	When Mars creates a new ID, CDS inactivates the older Mars ID(s).
5.3  Source Consumer Key (LS Customer ID)
	•	The LS-side customer identifier.
	•	If populated, it is a strong signal that the consumer is migrated.
	•	Used during migration to prevent duplicate consumers.

9.  Standard incident analysis — step by step
Follow these five steps in order. Do not skip ahead.
Step 1  —  Understand the ask
Before touching any data, clarify what is actually being reported.
	•	What exactly is missing or wrong? Consumer? Order? Loyalty points? Brand / civility / location?
	•	Which market / country?
	•	Which system raised the issue (CDS, Mars, Loyalty, SFMC, SA)?
	•	What does the requester expect to see?
Step 2  —  Identify data type (consumer vs purchase)
Consumer issues
Purchase issues
Cannot find consumer
Missing orders
Duplicate consumer
Incorrect order amount
Wrong details (civility, brand, status)
Loyalty points not awarded
Inactive Mars ID

Step 3  —  Check creation timing
Always pull both timestamps:
	•	Source creation datetime
	•	Order datetime (for purchases)
Compare against the market go-live (Section 4) to decide migrated vs ongoing. This decision determines which system owns the issue.
Step 4  —  Migration check (C2 LUCID)
If the record is migrated:
	•	Confirm Source Consumer Key is populated.
	•	Confirm LS Customer ID exists.
	•	If the record is missing in a downstream system, do NOT ask CDS to resend. LS is the owner of historical sends to CDS and Loyalty.

Correct action: route or escalate to LS. Do not raise a CDS downstream-extract request for migrated data.
Step 5  —  Ongoing data check (C5 LUCID)
If the record is ongoing:
	•	Confirm API ingestion success in CDS.
	•	Confirm consumer is present in CONSUMER_PII_TBL.
	•	Confirm Mars ID linkage in EXTERNAL_SYSTEM_IDS_TBL.
	•	If Mars does not have the consumer, confirm whether the CE nightly batch (incremental extract) has run and the consumer was picked up.

Correct action: ask the CE team for the file name and run confirmation, then ask Mars to ingest the file. Do not assume CDS is broken until you have evidence.
10.  Common incident patterns & correct handling
10.1  Loyalty points missing
Ask first: is the purchase migrated or ongoing?
	•	Migrated → LS is responsible for sending historical orders to Loyalty. CDS does NOT push historical purchases.
	•	Ongoing → check the downstream event/extract flow from CDS. Confirm the order exists in CDS first.

Common mistake: raising a defect on CDS for missing loyalty points without first confirming that the purchase is even in CDS, and without checking whether it is historical or live.
10.2  "Consumer not found in Mars"
Possible reasons:
	•	Mars never ingested the CDS extract.
	•	Mars ID is inactive (a newer one was created).
	•	Incremental extract was not triggered or the consumer was not in the delta window.
Correct handling:
	•	Confirm the consumer exists in CDS (CONSUMER_PII_TBL).
	•	Check EXTERNAL_SYSTEM_IDS_TBL for the Mars ID and its status.
	•	Ask the CE team when the extract last ran and whether this consumer was included.
	•	Ask Mars to ingest the relevant file.
10.3  Brand / civility / code mismatch
Example discussed in the session: Mars sending civility = 101, but CDS only accepts the standardised value 005.
	•	CDS follows a standardised code list. Unknown codes are rejected.
	•	This is not a CDS ingestion bug — it is a source data compliance issue.

Correct action: ask the source system (Mars in this example) to fix its mapping. Do not implement quick fixes in CDS to accept the bad code unless explicitly approved.
10.4  Missing orders
	•	Migrated → LS owns the historical send. Confirm whether LS sent the order to CDS / Loyalty.
	•	Ongoing → check the inbound MARS OrderHeader / OrderItem feeds for the date in question (file arrival, processing status).
	•	Always confirm the source order number, order datetime, and country signature before responding.
10.5  Incorrect order amount
	•	Pull the source order from the upstream system and compare with CDS PURCHASE_TBL.
	•	If CDS matches source → the issue is downstream (Loyalty / reporting). Do not patch CDS.
	•	If CDS does not match source → check the OrderHeader / OrderItem ingestion for that order date.
10.6  Brand / location data wrong
	•	Brand and location data often does not originate from CDS.
	•	If the issue is store / location related, identify the upstream system sending the metadata (typically Counter / BA feeds from MARS or CEGID).
	•	Avoid the default of routing every metadata issue to CDS.
11.  Status mismatch (PI vs External System ID)
Observed scenarios:
	•	PI status = inactive, External System ID = active (or vice versa).
Expected behaviour:
	•	Only one active Mars ID per consumer.
	•	Older Mars IDs are inactivated when a new one is created.

Action: verify the scenario before raising RCA. A status mismatch is not automatically a defect — it may be the expected lifecycle behaviour. Only escalate if it is genuinely inconsistent with the rule above.
12.  Common mistakes — what NOT to do
✗  Checking the wrong country / market.
✗  Jumping straight to merge requests or data patches without root cause.
✗  Asking CDS to resend migrated data — that is LS's responsibility.
✗  Providing RCA without verifying source creation dates.
✗  Responding without screenshots or model checks.
✗  Defaulting every metadata issue to CDS without identifying the upstream owner.
✗  Treating standardised-code rejections as CDS bugs.
13.  Expectations from L2 / L3 going forward
	•	Perform first-level analysis independently.
	•	Use the CDS data model and B2C Mapping Doc V3 to validate fields and routing.
	•	Bring specific, evidenced doubts to KT calls — not open-ended questions.
	•	Provide on every ticket: clear analysis, screenshots with all mandatory fields, and a logical conclusion.
	•	Escalate only when needed, with evidence.
14.  Final takeaway — the 3 questions
If you cannot solve an incident, it is almost always because one of these three questions has not been answered correctly. Answer them in order.

1.  What data is impacted?
    Consumer or purchase? Be specific.

2.  Is it migrated or ongoing?
    Use source creation datetime vs market go-live. Use LUCID prefix (C2 vs C5) to confirm.

3.  Which system owns that responsibility?
    Migrated → LS owns historical sends. Ongoing → CDS owns API + CE batch. Mars owns Mars ID.

If these are clear, the correct action becomes obvious.
